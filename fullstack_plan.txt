## Reality Check First

Your `main.py` is clean. You already have a working FastAPI app with three routers (parse, ingest, retrieve) and a smart lifespan hook. The core RAG is solid. What's missing is plumbing, not intelligence.

Here's the minimal path — no bloat, no over-engineering.

---

## Phase 1: Fix the Embarrassing Stuff (1 day)

**Step 1 — Rename the typo.** `data_processing,py` → `data_processing.py`. Do this first. It's the first thing anyone who clones your repo will notice.

**Step 2 — Add a `.env` file + `python-dotenv`.** Your `FAISS_INDEX_DIR` is already read from `os.environ`. Stop hardcoding defaults. Put config in `.env`, load it at startup. Anyone running your project shouldn't have to dig through code to change paths.

**Step 3 — Add `CORS` middleware to `main.py`.** Right now a browser can't call your API at all. Add FastAPI's `CORSMiddleware` allowing `localhost:5173` (Vite's default port). Without this, your future frontend will hit a wall immediately.

---

## Phase 2: The One Database Table That Matters (1–2 days)

Don't add PostgreSQL yet. That's yak shaving. Use **SQLite + SQLModel** — zero infrastructure, same API, you can swap to Postgres later with one line change.

**Step 4 — Create a single `documents` table.** Fields: `id`, `filename`, `status` (Processing / Success / Failed), `chunk_count`, `created_at`. That's it. No chunks table yet.

**Step 5 — Wire it into your existing `/api/ingest` endpoint.** Before ingestion starts, insert a row with status=Processing. When it finishes, update to Success with chunk count. If it throws, update to Failed. Your existing ingestion logic doesn't change at all — you're just bookmarking it.

**Step 6 — Add `GET /api/documents`.** Returns the list of rows. This is 5 lines of code. Now you have a real "what's indexed" endpoint instead of manually reading `metadata.json`.

---

## Phase 3: Make Ingestion Non-Blocking (half a day)

**Step 7 — Use `BackgroundTasks` in `/api/ingest`.** Right now your ingest endpoint blocks until the entire embedding is done. For a big PDF this could be 30+ seconds with a hung HTTP connection. Change it so the endpoint immediately returns `{"status": "Processing", "document_id": 5}` and the actual embedding happens in the background. The DB row you added in Phase 2 is how the client polls for status.

This is critical for the frontend to feel responsive. It also demonstrates you understand async properly — not just slapping `async def` on everything.

---

## Phase 4: Minimal React Frontend (2–3 days)

**Step 8 — Scaffold with Vite.** Run `npm create vite@latest frontend -- --template react-ts`. Don't use CRA, it's dead. Put the `frontend/` folder at repo root alongside your Python code.

**Step 9 — Build two components only.** Not a full app. Just two:

First, an **Upload component**. A file input (not drag-and-drop yet — that's a nice-to-have), a button that calls `POST /api/ingest` with `multipart/form-data`, and a status message. That's it.

Second, a **Document list component**. Calls `GET /api/documents` on mount with `useEffect`. Renders a table of filenames and statuses. Polls every 3 seconds if any row has status=Processing. This is the visual proof that your background task works.

**Step 10 — Add a Search bar.** One input, one button, calls `POST /api/retrieve`. Render the results below. For each result, show the source filename from metadata. This is the "Evidence Card" from the plan — but dead simple, just a div with a border.

---

## Phase 5: Docker Compose (half a day)

**Step 11 — Write a `docker-compose.yml` with two services.** Just `api` (your FastAPI app) and `frontend` (Vite dev server or nginx serving the built files). SQLite lives inside the api container — no separate DB service needed at this stage.

This is the one step that makes the whole thing "production-looking" to anyone reviewing the repo. `docker-compose up` → everything works. That's the signal.

---

## What to Skip (Seriously)

Don't add PostgreSQL until you actually need it. SQLite handles thousands of documents fine and eliminates an entire infrastructure dependency. Don't add react-dropzone, authentication, user accounts, or chunk-level tables. Those are all scope creep for what this project needs to demonstrate right now.

The full plan in the document you shared is good directionally, but it front-loads the hard infrastructure (Postgres, full CRUD) before proving the UI even connects. The order above gets you to a working demo faster and lets you add complexity on a solid foundation.
